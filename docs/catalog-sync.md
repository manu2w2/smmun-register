# Plan de sincronización de Google Sheets a Supabase

Propuesta preparada el 18 de noviembre de 2026. La carga manual por CSV está implementada. La automatización leerá las celdas directamente y enviará el mismo tipo de lote a `catalog.import_representations`. Así se reutilizan la comparación, la identidad y la escritura transaccional que ya se probaron con CSV.

## Estado de implementación

La Edge Function `supabase/functions/catalog-sync`, los roles, el registro de corridas, el límite compartido por proyecto de Google dentro de una misma base y el panel local están implementados. El SQL `supabase/operations/schedule-catalog-sync.sql` prepara el horario, que debe ejecutarse únicamente en el entorno de staging identificado. La sincronización automática no está activada.

La función requiere `CATALOG_SYNC_SECRET`, `CATALOG_EDITION`, `CATALOG_MODE` (`preview` o `apply`), `CATALOG_SPREADSHEET_ID`, `CATALOG_SHEET_ID`, `CATALOG_GOOGLE_PROJECT_KEY`, `GOOGLE_SERVICE_ACCOUNT_JSON` y `CATALOG_DATABASE_URL`. La conexión debe tener una sesión estable y asumir los permisos de `catalog_sync`. El trabajo programado necesita los secretos `catalog_sync_url` y `catalog_sync_secret` en Vault. Las credenciales son específicas de cada entorno y se mantienen fuera del repositorio.

Los límites compartidos dependen de la base de datos usada para registrar reservas. Si staging y producción usan bases distintas con el mismo proyecto de Google, sus presupuestos no se coordinan. Utiliza proyectos de Google separados o implementa una cuota compartida antes de activarlos simultáneamente.

El panel de desarrollo usa `npm run catalog:panel` después de `npm run build` y consulta únicamente Supabase local. El endpoint autenticado para staging, las alertas, la prueba con Google y la verificación de Edge Runtime siguen pendientes.

## Flujo por edición

1. **Resolver la fuente.** Configurar por entorno la edición, el ID del archivo, el ID de la pestaña y el modo (`preview` o `apply`). La [hoja de prueba](https://docs.google.com/spreadsheets/d/1zO-z01dyBUPBbhA-eroPf6CL3YBk5cpRl-yYEkwNoCU/edit#gid=0) usa la pestaña `catalogo` con ID `0`. Resolver su título actual a partir del ID. Leer A:D con `spreadsheets.values.get`, `majorDimension=ROWS` y `UNFORMATTED_VALUE`. La cuenta de servicio recibe acceso de lector al archivo y solicita el alcance `spreadsheets.readonly`. [Lectura de rangos](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get) · [Permisos de Sheets](https://developers.google.com/workspace/sheets/api/scopes)
2. **Validar el lote completo.** Exigir los cuatro encabezados actuales en cualquier orden. Omitir filas completamente vacías y conservar el número de fila de la hoja para diagnosticar errores. Recortar espacios, normalizar Unicode a NFC y aceptar casillas booleanas nativas además de las etiquetas admitidas por CSV. Rechazar todo el lote si la pestaña falta, la hoja está vacía, una fila está incompleta o un valor es inválido. PostgreSQL detecta duplicados con la misma identidad que utiliza al escribir. Usar los mismos casos de prueba para los adaptadores CSV y Sheets. [Contrato del catálogo](data-model.md#importación-por-csv)
3. **Comparar y aplicar.** En `preview`, calcular altas, cambios, iguales y ausentes mediante una consulta de solo lectura. En `apply`, invocar la función con `allow_missing = false` para comparar y escribir en la misma transacción. Si hay alguna ausencia, queda pendiente todo el lote. Un renombre requiere conciliar la identidad conservando el UUID antes de reanudar. Sheets administra las cuatro columnas de origen. PostgreSQL conserva `disponible` en filas existentes y lo inicia en `true` en las nuevas.

## Ejecución y permisos

- **Trabajo programado.** Supabase Cron llama a una Edge Function exclusiva para el catálogo **cada 20 minutos** (`*/20 * * * *` para una edición). Configurar también una invocación manual autenticada para pruebas. El modo y el destino salen de la configuración del entorno. El cuerpo de la petición no puede elegir la hoja, la base de datos ni el modo de escritura.
- **Credenciales.** Usar un secreto de invocación dedicado a esta función, en Vault para Cron y en los secretos de la Edge Function para validar la petición antes de acceder a Google o PostgreSQL. Guardar ahí también las credenciales de Google y el acceso a la base. El rol de PostgreSQL tendrá acceso al esquema y a la función, lectura del catálogo y permisos de escritura por columna para la importación, con políticas RLS explícitas. Probar que no puede modificar `disponible`, borrar filas ni acceder a otros datos. [Programación de Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions) · [Seguridad de Edge Functions](https://supabase.com/docs/guides/functions/auth)
- **Una corrida por edición.** Obtener un bloqueo de sesión de PostgreSQL antes de leer Sheets y mantenerlo hasta terminar la comparación o escritura. Usar la misma clave por edición que el bloqueo transaccional del importador. Usar una conexión que preserve la sesión y cerrarla en todos los resultados, con un tiempo máximo para la lectura externa. Una segunda ejecución se registra como omitida y la siguiente empieza con una lectura nueva. Para una carga manual, pausar el trabajo y esperar a que termine la corrida activa antes de exportar el CSV. [Conexiones de Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres)
- **Observación y fallos.** Registrar por corrida edición, modo, tiempos, resultado, hash del lote, conteos, intentos contra Google y respuestas `429`. La huella sirve para comparar corridas, y la comparación con PostgreSQL sigue siendo la que decide si hay cambios. Mantener el contenido de las celdas y los secretos fuera de los logs. Una validación fallida, una ausencia o varios fallos transitorios consecutivos requieren aviso al responsable del catálogo. Consultar el resultado de la sincronización además del estado de Cron, que solo confirma que se disparó la llamada.

## Presupuesto de uso de Google Sheets

- **Dos lecturas por corrida normal y cero escrituras a Google.** Una llamada a `spreadsheets.get` con máscara de campos resuelve el ID y el título de la pestaña. Otra llamada lee las cuatro columnas en bloque. A 20 minutos son **72 corridas y 144 lecturas al día por edición**, sin contar las invocaciones de prueba. La cuota pública se aplica por minuto, con **60 lecturas por usuario por proyecto y 300 por proyecto**. La cuenta de servicio cuenta como un usuario. Comprobar la cuota efectiva y el uso de otras integraciones en Google Cloud antes de activar el horario. [Cuotas de Sheets](https://developers.google.com/workspace/sheets/api/limits)
- **Reintentos acotados.** Admitir hasta dos reintentos por lectura ante errores transitorios de red, `429` o `5xx`, con espera exponencial y variación aleatoria. Respetar `Retry-After` cuando esté presente. Si la espera supera el tiempo disponible de la corrida, dejar el intento para el siguiente ciclo. Una corrida tiene un máximo de seis solicitudes, incluidas las fallidas. Si el lote no se obtiene completo, conservar el último catálogo válido.
- **Margen si crece el uso.** Aplicar un presupuesto interno de hasta 12 intentos de lectura en cualquier periodo de 60 segundos por proyecto de Google Cloud para este sincronizador, compartido por ejecuciones programadas y manuales que usen el mismo proyecto. Ajustarlo a la baja si la cuota real o el tráfico compartido lo requieren. Escalonar los horarios de las ediciones y no lanzar corridas de recuperación en ráfaga. Antes de activar, medir intentos en staging y simular un `429` para comprobar el límite, la espera y que la tabla queda intacta.

## Panel de consulta en Svelte

- Crear una vista interna de solo lectura en Svelte con una tabla sencilla. Mostrar edición, comité, representación, tipo, codelegación y disponibilidad. Filtrar por edición y comité.
- Encima de la tabla, mostrar la última corrida, la última actualización aplicada y los conteos de altas, cambios, iguales y ausentes. Indicar si la actualización está en curso, terminó sin cambios, se aplicó, necesita revisión o falló. Si falla, conservar las filas visibles y mostrar cuándo se actualizaron por última vez.
- Consultar PostgreSQL y el registro de corridas mediante un endpoint autenticado de solo lectura. Actualizar al abrir el panel y cada 60 segundos mientras la pestaña esté visible. Un botón **Actualizar vista** vuelve a leer el endpoint. Abrir el panel o pulsar el botón genera **cero llamadas a Google Sheets**. Mantener el acceso a PostgreSQL en el servidor, con permisos de lectura y sin exponer el esquema `catalog`. Probar el panel localmente y en staging con el runtime del endpoint.

## Orden de entrega y criterios de aceptación

| Paso | Entregable | Evidencia para avanzar |
| --- | --- | --- |
| 1. Adaptador local | Lectura de Sheets, validación y vista previa invocada manualmente. | Una hoja de prueba y su CSV equivalente producen las mismas diferencias. Se cubren casillas, blancos, encabezado incorrecto, duplicados y booleano inválido. |
| 2. Staging en vista previa | Proyecto Supabase y hoja sintética separados, credenciales propias y registro de corridas. | Una llamada sin credencial se rechaza. Los permisos del rol son los previstos. Dos llamadas simultáneas dejan una sola corrida activa. Una caída de Google o una hoja vacía deja el catálogo intacto. |
| 3. Staging con escritura | Ejecución manual y luego cada 20 minutos en modo `apply`. | Un alta inicia disponible. Un cambio de tipo o codelegación conserva UUID y disponibilidad. Repetir el lote escribe cero filas. Una ausencia o un renombre bloquea toda la escritura. Un `429` respeta el presupuesto de reintentos. |
| 4. Panel de consulta | Tabla y estado de sincronización en Svelte. | Un lote aplicado aparece al refrescar la vista. Si la siguiente corrida falla, la tabla conserva el último catálogo y muestra el error. Varias vistas abiertas generan cero consultas a Sheets. |
| 5. Activación | Edición y pestaña confirmadas, cuota efectiva comprobada y responsable de alertas identificado. | Revisar la primera vista previa con el mantenedor del catálogo. Tras autorizar el destino, aplicar el primer lote de forma controlada y comprobar sus conteos antes de activar el horario. |

## Pausa y recuperación

Desactivar el trabajo de Cron y esperar a que concluya la corrida activa. Corregir la hoja y ejecutar una vista previa. Si se requiere seguir operando mientras se investiga, usar el [procedimiento manual por CSV](operations.md#actualizar-el-catálogo). Si un lote válido ya escribió cambios equivocados, conciliar primero los UUID y la disponibilidad de las filas afectadas y aplicar una corrección revisada. Para reactivar el horario, repetir la vista previa y confirmar que no quedan ausencias sin resolver.
